## Intent

**Problem :** aucun Run ne peut encore apprendre. Il n'existe ni rendu de conversation par le chat template officiel avec les `chat_template_kwargs` du modèle, ni masque qui limite la perte aux tours `assistant`. On ne sait pas non plus si le texte rendu à l'entraînement est identique à celui de `llama-server --jinja` (H-MASQUE, FR-34, AD-7).

**Approach :** `slmsp.train.rendu` charge le tokenizer d'un candidat et rend une conversation canonique par `tokenizer.apply_chat_template`. Il reprend le template, les kwargs et la règle `tools` de l'inférence. `slmsp.train.masque` repère les tours `assistant` par rendu incrémental, puis passe des caractères aux tokens par les offsets du tokenizer rapide. Les labels valent −100 partout ailleurs. Les tests sur tokenizers réels consignent le résultat pour chaque candidat.

## Boundaries & Constraints

**Always :**
- Les imports de `transformers` se font **dans les fonctions** (comme dans `train/environnement.py`). Les tests unitaires tournent sans l'extra `train`, avec un tokenizer factice. Les tests réels appellent `pytest.importorskip("transformers")` et se sautent si `models/<slug>/` est absent.
- Les messages sont validés par `core.messages.valider_conversation`, puis convertis par `vers_dicts`. Les `arguments` des `tool_calls` restent des chaînes JSON, comme dans les requêtes envoyées à `llama-server`.
- Les règles d'inférence sont reproduites à l'identique :
  - kwargs = `ConfigModele.chat_template_kwargs` ;
  - `tools` n'est transmis au template que si `protocole_outils == "natif"` (même règle que `ClientLlama.compter_tokens`) ;
  - si `chat_template_force`, le template est celui de `models/<slug>/chat_template.jinja`, c'est-à-dire le fichier passé à `--chat-template-file`.
- Toute lecture passe par `core.artefacts` avec `lecteur="train"` (`chemin_autorise`, `lire_texte`). Aucun `open()`, `.read_text()` ni `json.load` dans `train/`.
- Tokenisation du texte rendu : `add_special_tokens=False` et `return_offsets_mapping=True`. Décodage : `skip_special_tokens=False` et `clean_up_tokenization_spaces=False`.
- Un tour `assistant` va de la fin du préfixe rendu avec `add_generation_prompt=True` jusqu'à la fin du rendu qui inclut ce message. Il comprend donc le contenu, les appels sérialisés par le template et la fin de tour.

**Never :**
- Pas de `assistant_only_loss` de TRL. Pas de troncature ni de padding : la longueur maximale relève de la 10.4.
- Pas de réseau ni de LLM. Pas d'exemple d'entraînement rédigé : les conversations de test sont synthétiques et aléatoires (graine fixe).
- Aucune modification hors de `src/slmsp/train/{rendu,masque}.py`, `tests/train/test_masque.py`, `tests/train/test_rendu.py` et, seulement en cas d'échec réel (AC2), `config/templates-entrainement/<slug>.jinja`.
- Ne pas modifier `inference/`, `core/` ni `mcp/`. Ne pas importer `fetch`, `data`, `measure` ni `evaluation`.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|---|---|---|---|
| Multi-tours avec outils | system, user, assistant(`tool_calls`), tool, assistant(texte) | `labels[i] = input_ids[i]` sur les tokens des 2 tours assistant, −100 ailleurs. Les segments décodés sont égaux aux intervalles du rendu | — |
| Aucun tour assistant | system + user | — | `ErreurMasque` |

| Conversation invalide | `tool_call_id` orphelin | — | `ConversationInvalide` propagée |
| `json-generique` (Qwen) | `tools` fourni | rendu sans `tools` | — |
| Template forcé absent | `chat_template_force = true`, fichier manquant | — | `ConfigurationInvalide` |

## Design Notes

Rendu incrémental, pour chaque index `i` d'un message assistant :

```python
avant = rendre(msgs[:i], add_generation_prompt=True)
avec = rendre(msgs[: i + 1])
if not avec.startswith(avant) or not complet.startswith(avec):
    raise ErreurMasque(f"message {i} : rendu non incrémental")
intervalles.append((len(avant), len(avec)))
```

Les templates de Granite et de Ministral peuvent insérer une date (`strftime_now`). Il faut donc rendre la référence et le texte comparé dans la même exécution. Un template qui modifie les tours passés (suppression du raisonnement, par exemple) échoue par construction : c'est le déclencheur du repli AC2.

## Décisions prises sans l'utilisateur

- Les signatures de l'interface imposée sont fixées ci-dessus : tokenizer passé explicitement, `config` facultative. L'option écartée, `apply_chat_template(messages, tools)` liée à un état global, rendait les tests factices impossibles.
- `arguments` des `tool_calls` gardés en chaîne JSON. Option écartée : la conversion en objet, qui ferait diverger `tojson` entre Jinja Python et le moteur Jinja de llama.cpp.
- Template forcé lu depuis `models/<slug>/chat_template.jinja`, le fichier servi par `llama-server`. Option écartée : se fier au template embarqué du tokenizer.
- `tools` reçu en paramètre et non lu par `rendu`, parce que `config/outils-mcp.toml` est hors de la liste d'accès `train`. Option écartée : étendre `chemin_autorise` (hors zone).
- `tools` retiré en `json-generique`, comme à l'inférence. Option écartée : le transmettre toujours.
- Token à cheval sur une frontière : `ErreurMasque`. Options écartées : l'inclure ou l'exclure en silence (masque inexact).
- `calculer_masque` renvoie un `dict` `input_ids`/`labels`, le format d'échange prévu pour la 10.5. Option écartée : un nouveau type exporté.
- Aucune troncature : elle relève de la 10.4. Option écartée : un paramètre `longueur_max` ici.
- Résultats par candidat consignés dans `## Implementation Notes`. Option écartée : un nouvel artefact de run.
- Variante de repli rangée sous `config/templates-entrainement/<slug>.jinja`, et seulement en cas d'échec. Option écartée : l'écrire d'office pour chaque candidat.
- Tests de rendu séparés dans `tests/train/test_rendu.py`. Option écartée : tout regrouper dans `test_masque.py`.
- Spec gardée en un seul fichier malgré une taille supérieure à 1600 tokens : rendu et masque forment un objectif unique. Option écartée : scinder.
