## Intent

**Problem:** Aucune Architecture ne précharge le Corpus dans le cache de prompt du fournisseur. On ne peut donc pas mesurer une approche sans recherche dont le coût d'indexation est explicite (FR-22).

**Approach:** Ajouter l'Architecture `cag` (`Cag`), qui reprend `long_context` : même index, un bloc étiqueté par Ancrage, même `check`, Réponse `cited`. Elle déclare `requires_prompt_cache: true`. Son `load` émet, par la passerelle, un appel de préchargement dont le system est exactement celui des appels `generate` suivants, avec `cache_system: true`, au poste `indexing` fixé par le runner.

## Boundaries & Constraints

**Always:**
- `Cag` est enregistrée `("architecture", "cag")` dans `wavelibrarian.architectures.cag`. Capacités : `retrieval_method="cited"`, `full_corpus_in_prompt=True`, `requires_prompt_cache=True`.
- Le préchargement a lieu dans `load`, jamais dans `index`. Le runner appelle `load` sur une instance neuve dans les deux cas, index construit ou servi par le cache : le préchargement est donc identique.
- Le system du préchargement est identique, octet pour octet, à celui des appels `generate` de `answer`, marqueur de rôle compris : rôle `generate`, même Contexte. Sans cela, le préfixe en cache ne sert pas.
- Le Generator est `llm` avec `cache_system: true`, forcé comme dans `long_context`. Seule la passerelle trace.

**Never:**
- Modifier le runner, la passerelle, le Rapport, `long_context.py` ou le Catalogue.
- Ajouter un rôle LLM.
- Comparer le Corpus à `min_cacheable_tokens` dans `Cag` : le préchargement part toujours.
- Faire un appel dans `check`.

## Design Notes

L'appel de préchargement passe par `complete` et non par `complete_structured`. Avec `max_tokens=1`, un vrai fournisseur ne rend pas de JSON valide, et le texte de cet appel n'est jamais lu. Le Faux LLM rend sa sortie `generate` par défaut, sans validation. Le Cache de réponses de la passerelle peut servir le préchargement lors d'une reprise. C'est pourquoi l'AC exige les tokens en cache sur la 2ᵉ Question : la 1ʳᵉ réécrit alors le préfixe chez le fournisseur.

Report hérité, non traité ici : la Configuration `cag` dans `experiments/mini-test.yaml`, `tests/conformance/test_architectures.py` et `tests/e2e/test_sm3.py` sont absents du dépôt (story 4.14). Comme en 6.1 à 6.4, ils restent à passer quand ils existeront.

## Décisions prises sans l'utilisateur

- Préchargement dans `load`, comme le demande la story, et non dans `index` comme le dit AD-8. Écarté : `index`, qui ne repréchargerait pas quand l'index est servi par le cache.
- Préchargement porté par une méthode `LLMGenerator.precharger` qui partage la construction du system. Écarté : une requête construite dans `Cag`, au risque d'un préfixe divergent.
- Rôle `generate`, step `cag.preload`, pour que le marqueur de rôle et donc le préfixe soient identiques. Écarté : un nouveau rôle `preload`, qui casserait le préfixe et toucherait `roles.py`.
- `gateway.complete` avec `max_tokens=1`. Écarté : `complete_structured`, qui échouerait sur un vrai fournisseur.
- `Cag` hérite de `LongContext` (index, `check`, `answer`, contexte parfait sans cache). Écarté : un module dupliqué.
- Generator autre que `llm` refusé (`ConfigError`). Écarté : l'accepter comme `long_context`, puisqu'il ne saurait pas précharger.
- `min_cacheable_tokens` non contrôlé : seul le fournisseur l'applique. Le test vérifie que le préchargement réussit, pas les tokens nuls, que le Faux LLM ne simule pas. Écarté : modifier `FakeProvider` ou la passerelle, hors périmètre.
- `passage_id` repris de `long_context` (graine `"long_context"`). La clé d'index diffère déjà par le nom d'Architecture. Écarté : paramétrer la graine, ce qui toucherait `long_context.py`.
