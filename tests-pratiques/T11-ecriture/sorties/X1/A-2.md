J'ai passé deux jours à vérifier ce que valent vraiment les outils censés rendre les agents de code moins chers ou meilleurs. Pour cela, j'ai mené 15 tests pratiques sur mes propres projets et sur 45 jours de transcriptions Claude Code.

Verdict : aucun des dépôts de ma liste de veille ne fait strictement mieux que l'option la plus simple.

**Ce qui rapporte (mesuré) :**
• Réduire le contexte fixe. 8 outils rarement utilisés ajoutaient 17,8 k tokens à chaque appel.
• Demander un second avis à Haiku avant la revue. 87 % des problèmes sérieux qu'il a relevés ont été corrigés, pour 0,03 $ par story.
• Confier l'implémentation à Sonnet seul. Il coûte 0,53 $ par story, contre 1,33 $ pour Opus, avec le même taux de réussite.
• Vérifier les critères d'acceptation dans un vrai navigateur. Dans mes tests de design, c'est le seul contrôle qui a repéré un écart.

**Ce qui ne rapporte pas (mesuré aussi) :**
• un relecteur d'une autre famille de modèles (+6 points, écart non significatif) ;
• le verrouillage des tests (aucune triche sur 40 runs) ;
• /advisor ;
• les tests property-based ;
• les juges de commandes shell ;
• la compression des sorties ;
• les modèles locaux pour l'usage courant ;
• l'allègement d'un CLAUDE.md de quelques milliers de tokens.

**La vraie découverte : la mutation guidée.** On lance des tests de mutation sur le code de la story, puis on montre à l'agent les mutants qui survivent à ses tests. Résultat : il a comblé 134 trous non équivalents sur 134. Avec une simple consigne du type « renforce tes tests », il n'en comblait que 59 %. Coût : 0,22 $ par story. Il a aussi identifié sans erreur les 35 mutants équivalents. C'est le seul ajout à ma chaîne que les tests justifient, sous forme d'étape optionnelle de la revue.

La leçon à retenir : avant d'ajouter un outil, mesurez-le sur vos propres données. Les gains viennent plus souvent de ce qu'on retire que de ce qu'on ajoute.
