# Digest — dimension `revue-securite` (tour 1, 2026-10-24)

Chercheur : sous-agent Opus 5.5. Budgets consommés : 25/25 appels web, ~16/20 lectures de dépôt. Arrêt : budget web épuisé (les questions principales étaient couvertes ; restent ouvertes les pistes listées en section 5). Un seul passage de recherche structuré en trois vagues (large → outils → contradictions).

## 1. Résumé

- Anthropic ne publie **ni taux de faux positifs, ni coût, ni modèle** pour sa revue interne ; ce qu'elle publie est une **architecture** (chercheurs en parallèle → vérificateurs qui votent → tri Important/Nit/Pre-existing) et des **règles de convergence** (plafond de 3 passes, revue du seul nouveau diff, signaler la classe de bug) [A1–A4]. Ce sont ces règles, plus que l'architecture, qui se transposent à un dev solo.
- Pour un abonné **Max**, le produit managé *Code Review* est **inaccessible** (Team/Enterprise) [A5] ; restent `/code-review` (local, sur le quota) [A7], `/code-review ultra` (3 essais gratuits puis 5 à 25 $ la revue) [A8], `/security-review` [A12].
- Les mesures publiques de précision des revues par LLM restent **basses** : 8 à 40 % selon l'approche sur AACR-Bench [A14], 34 % au mieux sur le banc (éditeur) d'open-code-review [A16]. Plus de commentaires = plus de rappel et moins de précision ; le compromis est structurel.
- Le **consensus entre agents ne prouve rien** : dix relecteurs unanimes ont validé une vulnérabilité inexistante, réfutée par un seul test [A20]. La vérification qui marche est **adversariale et empirique** (PoC qui échoue sur le code d'origine, modèle différent pour valider) [A11, A20].
- **open-code-review** : bonne idée (déterministe pour le choix des fichiers et les règles, LLM pour le jugement), ~1/15 des tokens de Claude Code sur le banc de l'éditeur, mais une reproduction indépendante (10 PR) a donné l'inverse (12 % de précision) avant un correctif annoncé [A16, A17]. → **Essayer** en mode délégation.
- **cloudflare/security-audit-skill** : méthode solide (6 phases, vérificateur frais qui tente de réfuter), mais **ses validateurs échouent sous Windows natif** (code lu : `O_NOFOLLOW` absent sous Node/Windows), correctif en PR non fusionnée, dépôt peu actif malgré 43 k étoiles [A22–A24]. → **Évaluer** (sous WSL).
- **SkillSpector** : scanner statique + LLM de skills/MCP, couvre explicitement les contournements publiés par Trail of Bits (.pyc, exécutable dans un .docx) [A27], mais **aucun taux de détection publié** pour l'outil lui-même ; les scanners de skills ont tous été contournés en < 1 h (ToB) ou à > 90 % (SkillCloak) [A30, A31]. → **Essayer** en `--no-llm` comme garde-fou d'installation, jamais comme preuve d'innocuité.

## 2. Fiches outils

### 2.1 alibaba/open-code-review (OCR)

**Ce que c'est.** CLI Go (`ocr`, installée par npm ou binaire de release) qui lit un diff Git, sélectionne les fichiers de façon déterministe, les regroupe en « bundles » revus chacun par un sous-agent à contexte isolé, applique des règles choisies par moteur de gabarits, puis passe les commentaires dans des modules externes de **positionnement** et de **réflexion** [A15]. Modes : `review` (diff), `scan` (fichiers entiers), sortie JSON, reprise de session, CI (GitHub Actions, GitLab…), serveur MCP pour étendre l'agent de revue. **Mode délégation** : OCR choisit les fichiers et résout les règles, et c'est l'agent hôte (Claude Code) qui fait la revue avec son propre modèle — pas de clé API séparée [A15].
**Injection de contexte.** Le plugin Claude Code n'installe que deux commandes (`review.md` 1,7 ko, `delegate-review.md` 3,1 ko), chargées seulement à l'appel ; pas de hook. Les skills portables pour d'autres agents font 12,9 ko et 9,3 ko (chargés à l'activation) — mesuré dans l'arbre du dépôt.
**Problème résolu.** Les trois défauts qu'OCR attribue à une revue par agent généraliste : fichiers sautés sur gros diff, lignes mal positionnées, qualité instable selon le prompt [A15].
**Preuves.**
- Banc de l'éditeur (AACR-Bench, 200 PR, 1 505 défauts annotés ; publié en image seulement) : OCR + Claude Opus 4.6 → précision 33,9 %, rappel 20,0 %, F1 25,1 %, 385 k tokens/revue ; Claude Code v2.1.169 + Opus 4.6 → précision 7,2 %, rappel 28,9 %, F1 11,6 %, 5 664 k tokens [A16]. Soit ~15× moins de tokens, plus de précision, **moins de rappel**. Biais : AACR-Bench est co-signé par cinq auteurs d'Alibaba [A14] ; version de Claude Code ancienne et mode d'appel (prompt, `/code-review` ou non) non documenté.
- Reproduction indépendante (HN, eranation, 10 PR du banc Martian) : ~74 % de rappel, ~12 % de précision — inverse du profil annoncé. Le chef de projet invoque une anomalie d'appel d'outil corrigée depuis, sans nouvelle mesure indépendante [A17]. Échantillon minuscule, source secondaire.
- Chiffres d'usage interne (« dizaines de milliers de développeurs, millions de défauts ») : affirmation de l'éditeur, non vérifiable [A15].
**Maturité.** Créé le 2026-05-18, 48 195 étoiles, 100 contributeurs et 100 commits sur 90 j (plafonds de la collecte probables), release v1.13.3 du 2026-10-22, Apache-2.0, badge OpenSSF Gold. Anomalie : 48 k étoiles en 5 mois (effet de lancement, cf. HN 284 points) ; activité réelle par ailleurs forte.
**Risques.** Envoie le code au fournisseur LLM configuré (sauf délégation). Télémétrie OpenTelemetry **désactivée par défaut** (`Enabled: false`, exportateur console, journalisation du contenu à `false`, code lu dans `internal/telemetry/config.go`). Règles d'origine en chinois, traduites depuis [A17]. Installation npm globale = code tiers exécuté localement.
**Compatibilité.** Windows annoncé et code spécifique Windows présent (`*_windows.go`) ; bogues Windows ouverts côté extension VS Code et OpenCode (processus orphelins, résolution de `npm.cmd`) [A19], pas sur la CLI elle-même d'après les titres. Plugins Claude Code, Codex, Cursor, Kimi, OpenCode → bonne portabilité pour les clients. Fournisseurs OpenAI/Anthropic-compatibles → routable vers Ollama à tester.
**Équivalent Anthropic.** `/code-review` (local) et `/code-review ultra` [A7, A8] ; Code Review managé (Team/Enterprise) [A5].
**Verdict : Essayer** — le mode délégation coûte peu à tester et vise précisément le défaut de couverture des gros diffs, mais le seul chiffre indépendant contredit le banc de l'éditeur.

### 2.2 cloudflare/security-audit-skill

**Ce que c'est.** Une skill (agent-neutre, installée par `npx skills add`) qui orchestre des sous-agents en six phases : reconnaissance (architecture, frontières de confiance, `coverage-ledger.json`), chasse pilotée par la couverture avec « critiques de couverture », validation de chaque candidat par un **vérificateur frais qui tente de le réfuter**, sortie structurée (`confirmed` / `needs_validation` / `rejected`) validée par schéma, **re-vérification indépendante** des enregistrements finaux, rapport [A21]. Deux validateurs Node sans dépendance. Deux modes : *guidance* (par défaut) et *full audit* (sur demande explicite) [A22]. Les exécutions successives sont additives (une passe trouve « environ la moitié » de ce que trouvent des passes répétées, selon Cloudflare) [A21].
**Injection de contexte.** Description de la skill : ~390 caractères relus à chaque appel ; `SKILL.md` 22 ko à l'activation ; 13 fichiers de classes d'attaque et de phases (~170 ko) chargés à la demande ; validateurs ~62 ko (exécutés, non lus). Mesuré dans l'arbre du dépôt.
**Problème résolu.** Audit de sécurité profond d'un dépôt avec constats vérifiés et lisibles par machine ; c'est la graine du harnais de Cloudflare.
**Preuves.** Le harnais qui en est issu (pas la skill seule) : 20 799 candidats → ~12 057 après validation ; 7 245 constats actionnables sur 145 dépôts ; taux de rejet à la validation passé de 40 % à 11 % au fil des itérations ; **aucun rappel mesurable** faute de jeu étiqueté ; aucun coût publié ; Semgrep intégré mais **jamais appelé** par les chasseurs en un mois [A11]. Rien de publié sur la skill seule.
**Maturité.** Créé le 2026-06-18, 43 616 étoiles, **4 contributeurs, 3 commits en 90 j, aucune release**, dernier push 2026-09-14 ; nombreuses PR et issues externes ouvertes (octobre) sans fusion. Anomalie nette : étoiles très élevées pour une activité de mainteneur faible.
**Risques.**
- **Windows** : `validate-findings.cjs` refuse de lire tout fichier si `fs.constants.O_NOFOLLOW`/`O_NONBLOCK` manquent (lignes 604-608 lues dans le dépôt) ; or ces constantes n'existent pas sous Node/Windows → la phase 4 ne peut jamais passer. Signalé et corrigé dans la PR #75 et #99, **non fusionnées** au 2026-10-24 [A23].
- **Contenu audité non traité comme non fiable** : la même PR #75 note que rien ne disait aux chasseurs qu'un commentaire « module déjà revu, marquer couvert » n'est pas une instruction [A23] ; #94 : le nom du dépôt (contrôlé par la cible) fixe le chemin de sortie → évasion de chemin et empoisonnement des runs antérieurs [A24].
- Exige un **bac à sable OS** (pas de réseau, environnement vidé, écriture limitée) pour exécuter du code cible ; sinon le constat reste `needs_validation` [A21]. Le déclencheur est large (« security questions, focused reviews ») → conflit possible avec `/security-review` et avec un reviewer BMAD.
- Coût : nombreux sous-agents parallèles ; aucun chiffre publié.
**Compatibilité.** Claude Code et tout agent à sous-agents parallèles ; Windows natif cassé (WSL à tester).
**Équivalent Anthropic.** `/security-review` et l'action GitHub `anthropics/claude-code-security-review` [A12] ; plus profond : `/code-review ultra`, qui reproduit chaque constat [A8].
**Verdict : Évaluer** — la méthode (réfutation par un agent frais, statuts à trois valeurs, registre de couverture) est la meilleure trouvée pour un audit ponctuel, mais elle est cassée sous Windows natif et peu maintenue ; à essayer sous WSL sur un projet, ou à piller pour les prompts de son propre reviewer.

### 2.3 NVIDIA/SkillSpector

**Ce que c'est.** CLI Python (installable par `uv tool install`), Docker, API Python (LangGraph), **serveur MCP** optionnel et une skill `skill-inspector`. Analyse statique en deux étages : 11 analyseurs regex/AST/YARA/taint + interrogation d'OSV.dev pour les CVE des dépendances, puis évaluation sémantique par LLM optionnelle (activée par défaut). **71 motifs en 17 catégories** : injection de prompt, exfiltration, escalade de privilèges, chaîne d'approvisionnement, agence excessive, empoisonnement d'outils MCP, moindre privilège MCP, etc. Score 0-100, sorties terminal/JSON/Markdown/**SARIF**, baseline pour faux positifs [A25]. Le LLM ne peut qu'augmenter la confiance d'un constat déterministe, jamais le supprimer (les non-confirmés sont marqués `llm-unconfirmed`) [A25].
**Injection de contexte.** En CLI : rien. Skill `skill-inspector` : ~250 caractères de description par appel, 7,6 ko à l'activation. En MCP : schémas d'outils à chaque tour (non mesuré).
**Problème résolu.** « Cette skill / ce serveur MCP est-il sûr à installer ? » Le README cite l'étude « Agent Skills in the Wild » : 26,1 % des 31 132 skills analysées vulnérables, 5,2 % probablement malveillantes [A25, A28].
**Preuves.** **Aucun taux de détection publié pour SkillSpector.** Les 86,7 % de précision / 82,5 % de rappel de l'article concernent **SkillScan**, l'outil des chercheurs (14 motifs), pas SkillSpector [A28]. Le README admet « précision modérée (des faux positifs) » pour l'étage statique [A25]. Issues ouvertes récentes : faux positif P5, détections manquées (shell=True imbriqué, ransomware multi-ligne, configs MCP de Claude Code non vues par AS2) [A29]. Il couvre explicitement deux techniques de Trail of Bits : bytecode `.pyc` livré (SC8) et exécutable caché dans un conteneur de document (SC9) [A27] — non testé de façon indépendante.
**Maturité.** Créé le 2026-03-21, 21 220 étoiles, release v2.13.1 du 2026-10-23, Apache-2.0, activité forte. Fait partie de la chaîne « NVIDIA Verified Skills » [A25].
**Risques.** LLM activé par défaut → le contenu des fichiers part chez le fournisseur (`nv_build` par défaut) ; `--no-llm` garde tout en local, mais SC4 envoie les noms de dépendances à OSV.dev [A25]. Ne sandboxe rien, n'exécute pas la skill [A25]. Pas de télémétrie relevée ; un compteur d'usage d'inférence est produit localement [A25].
**Compatibilité.** **Sous Windows, l'écriture de fichier `--output` est indisponible** (opérations POSIX no-follow) ; utiliser la sortie standard [A26]. Fournisseurs : Anthropic, Bedrock, **CLI Claude locale (session Max, sans clé)**, **Ollama**, OpenAI-compatibles [A25]. Scanne skills Claude Code, Codex, Gemini CLI, MCP.
**Équivalent Anthropic.** Aucun scanner de skills natif trouvé dans la doc consultée. Trail of Bits recommande les marketplaces curées et les plugins gérés par l'organisation plutôt qu'un scanner [A30].
**Verdict : Essayer** — en CLI `--no-llm` (ou provider `claude_cli`/Ollama) comme contrôle avant d'installer une skill tierce ; jamais comme garantie, vu les contournements publiés.

### 2.4 Natif Anthropic et chaîne maison (comparaison demandée)

| Option | Où / qui | Coût pour un Max | Vérification des constats | Remarques |
|---|---|---|---|---|
| Code Review (GitHub, managé) | Infra Anthropic, **Team/Enterprise seulement** [A5] | n/a | Étape *Verify* qui filtre les faux positifs ; niveaux Quick/Standard/Deep ; ne bloque ni n'approuve la PR [A5] | Facturé à l'usage, sans prix fixe ; `REVIEW.md` lu depuis la branche de base [A6] |
| `/code-review` (alias `/review`) | Session locale, sous-agent en arrière-plan [A7] | Sur le quota du plan | `low` = constats les plus sûrs, `medium`→`max` = couverture plus large ; `--fix`, `--comment`, `--max-findings` [A7] | Lit `CLAUDE.md`, **pas** `REVIEW.md` ; remplaçable par une skill projet nommée `code-review` [A7] |
| `/code-review ultra` (ultrareview) | Bac à sable cloud, flotte d'agents [A8] | 3 essais gratuits (une fois), puis **5 à 25 $** en crédits d'usage [A8] | **Chaque constat reproduit et vérifié indépendamment** [A8] | 15–25 min ; limite 500 fichiers / 8 000 lignes ; `claude ultrareview` pour la CI [A8] |
| `/security-review` + action GitHub | Local / CI | Quota / API | Filtrage des faux positifs par règles d'exclusion et prompt [A12] | Action **non durcie contre l'injection de prompt** (PR de confiance seulement) ; modèle par défaut Opus 4.1, dernier push 2026-02 [A12] ; Checkmarx l'a trompée par un commentaire et par du code découpé, et elle a exécuté une requête SQL réelle [A13] |
| Chaîne maison Sonnet → Haiku → Opus | Session locale | Quota | Haiku adversarial puis Opus juge | Même famille de modèles : ne couvre pas les angles morts corrélés [A20] ; pas de porte empirique |

**Ce qui est transposable de l'article d'Anthropic à un dev solo** [A1–A4] :
1. **Plafond de 3 passes de revue**, et après la première passe, revoir **seulement le nouveau diff** ; ne pas répéter un constat déjà publié ; signaler la **classe** de bug plutôt que la ligne (59 % des constats répétés portaient sur du code déjà présent à la première passe). Directement applicable au couple dev-story/reviewer.
2. **Filtrer style, diagnostics et nettoyage** : le bruit coûte plus cher quand l'auteur est un agent (chaque nit = un commit + un tour de revue).
3. **Étiquettes Important / Nit / Pre-existing** : seul Important bloque.
4. **Chaque incident devient un cas d'évaluation** du reviewer, rejoué à chaque changement de prompt ou de modèle.
5. Mesurer la convergence : part des PR validées après une passe (65 % → 78 % chez Anthropic), PR à 5 passes ou plus (8,9 % → 1,5 %), revues moyennes avant validation (2,08 → 1,32) [A3].
Non transposable : le vote entre plusieurs vérificateurs (coût) — et de toute façon insuffisant sans test [A20].

## 3. Analyse de catégorie

### Doublons et complémentarités
Les trois outils ne se recouvrent pas : OCR = revue de diff (correction), security-audit-skill = audit de sécurité d'un dépôt entier, SkillSpector = contrôle de la chaîne d'outils de l'agent. Doublons réels :
- **OCR vs `/code-review`** : aucun n'est strictement meilleur. OCR gagne sur le coût en tokens et la précision *selon l'éditeur* [A16], et sur la portabilité (Codex, Cursor) ; `/code-review` gagne sur l'intégration (zéro installation, `--fix`, mémoire du niveau d'effort) et sur le rappel du même banc [A16].
- **security-audit-skill vs `/security-review` vs ultrareview** : la skill est la plus rigoureuse sur la vérification (vérificateur frais, statut `needs_validation`), ultrareview reproduit les constats sans rien installer mais coûte 5-25 $ après 3 essais, `/security-review` est le plus léger et le plus facile à tromper [A13].
- **SkillSpector vs Snyk Agent Scan** : Snyk Agent Scan (ex-mcp-scan d'Invariant Labs, v0.6.9 du 2026-10-20, Apache-2.0) découvre automatiquement les composants installés (Claude Code sous Windows : MCP et skills ✓) mais **exige un jeton Snyk** et l'analyse passe par l'API Snyk ; scanner une config MCP **lance les serveurs stdio** — à faire en bac à sable [A32]. SkillSpector fonctionne hors ligne (`--no-llm`) et produit du SARIF. Ni l'un ni l'autre ne publie de taux de détection trouvé ce tour.

### État de l'art hors liste
- **Hybride SAST + filtre LLM** : QASecClaw (préprint) F1 90,9 % contre 78,4 % pour Semgrep seul sur OWASP Benchmark v1.2, faux positifs 560 → 64 pour −3,1 % de rappel [A33]. Benchmark Java synthétique ; mais l'idée (Semgrep/CodeQL en entrée, LLM en juge) est bon marché et compatible avec ruff/CI. À l'inverse, chez Cloudflare les agents n'appelaient jamais Semgrep [A11] : il faut l'imposer dans le pipeline, pas l'offrir comme outil.
- **Critique d'une autre famille de modèles + porte empirique** (Refute-or-Promote) : ~79 % des 171 candidats éliminés avant divulgation ; un critique d'une autre famille attrape des angles morts corrélés ; dix relecteurs unanimes ont validé un faux positif qu'un seul test a réfuté [A20]. Cloudflare utilise lui aussi un modèle différent pour valider [A11].
- **Agrégation de plusieurs passes** : GitHub rapporte, sur Copilot lite, +13,6 % de rappel, −8 % de coût par revue et +8 % de commentaires suivis de modifications en combinant plusieurs exécutions [A34]. ReviewBench (219 PR, 187 dépôts, 19 langages) : meilleur F1 « grounded » 40,1 % (Copilot) selon la presse [A34, A35].
- **Précision des revues LLM** (littérature) : AACR-Bench — agent Claude Code + Sonnet 4.5 : précision 39,9 %, rappel 10,1 % ; LLM seul sans contexte : précision 8,7 %, rappel 42,9 % ; le contexte récupéré (BM25, embeddings) peut ajouter du bruit [A14]. Ordre de grandeur cohérent entre sources : **un commentaire sur deux à trois est faux même dans le meilleur cas** (borne basse : la vérité terrain est incomplète).
- **Défense des skills** : Trail of Bits — ClawHub, Cisco skill-scanner et les trois scanners de skills.sh (Gen, Socket, Snyk) contournés, trois skills sur quatre en moins d'une heure ; recommandation : marketplaces curées, versions épinglées, « treat public skill repositories as untrusted code » [A30]. SkillCloak (HKUST, préprint) : > 90 % d'évasion sur huit scanners, 1 613 skills malveillantes ; contre-mesure proposée : audit à l'exécution (SkillDetonate) [A31]. Attaques réelles en 2026 : campagne ClawHavoc sur ClawHub (chiffres divergents selon les sources, 1 184 ou ~900 skills) et vol d'identifiants via skills (AMOS Stealer) — sources secondaires [A36].

### Problèmes que rien ne traite encore
- **Rappel inconnu** : ni Anthropic, ni Cloudflare, ni SkillSpector ne publient de faux négatifs ; Cloudflare dit qu'ils ne sont pas mesurables sans jeu étiqueté [A11].
- **Injection de prompt contre le reviewer lui-même** : action `/security-review` non durcie [A12], skill Cloudflare corrigée seulement en PR [A23], Checkmarx a obtenu « 0 vulnérabilité » par un commentaire [A13]. Aucun outil de la liste ne mesure sa propre robustesse.
- **Détection à l'exécution des skills** : les scanners sont statiques et contournables [A30, A31] ; rien de prêt à l'emploi sous Windows pour auditer le comportement d'une skill pendant qu'elle tourne.
- **Coût réel d'une revue** : ni Anthropic ni Cloudflare ne le publient ; seul OCR donne des tokens (banc éditeur).
- **Pas de taux de faux positifs pour `/security-review`** trouvé ce tour.

### Hypothèses à tester en pratique
1. **OCR délégation vs `/code-review` vs reviewer maison.** Tâche : 5 PR passées d'un projet FastAPI dont on connaît les bugs corrigés ensuite (+ 2 bugs injectés par PR). Mesures : constats vrais / faux, bugs manqués, tokens (`/agent-cost-kit:mesurer-couts`), durée. Décision : adopter OCR si précision ≥ celle du reviewer maison et tokens ≤ 50 %.
2. **Critique d'une autre famille.** Remplacer (ou doubler) le second avis Haiku par un modèle d'une autre famille (Codex/GPT ou modèle Ollama ≤ 4B) sur les mêmes 5 PR. Mesure : constats « high » réfutés à tort / à raison. Décision : garder si au moins un faux « high » d'Opus est éliminé sans perte de vrai bug.
3. **Porte empirique.** Exiger du reviewer un test qui échoue pour tout constat Important. Mesure : part des Important qui survivent, tokens en plus. Décision : garder si les faux Important baissent de moitié pour < 30 % de tokens en plus.
4. **Règles de convergence d'Anthropic** (3 passes max, nouveau diff seulement, nits non bloquants) sur un sprint : mesurer passes par story et constats répétés avant/après.
5. **SkillSpector et Snyk Agent Scan sur 10 skills connues** (5 saines dont BMAD et agent-cost-kit, 5 fixtures malveillantes du dépôt SkillSpector et les techniques ToB reproduites à la main sans charge réelle) : faux positifs sur les skills saines, détections, temps. Décision : brancher en garde-fou d'installation si 0 faux bloquant sur les saines.
6. **security-audit-skill sous WSL** sur un petit projet FastAPI avec 3 vulnérabilités semées (IDOR, injection SQL, SSRF) contre `/security-review` et Semgrep : vrais/faux constats, tokens, durée.
